# ADR-002 实现语言与仓库结构

- 状态：已接受（M0）
- 日期：2026-11-09
- 关联：路线图第 5、12、14 节

## 结论

采用 **Java 写前端与驱动 + C 写运行时与 C 后端** 的分工：

- 前端（词法、语法、AST、语义、HIR、MIR）用 Java 25，使用 `record` / `sealed` / 模式匹配描述语法树。
- MIR 先降为 C（带 `#line`），由 clang `-O2` 编译为目标文件，再链接 C 运行时。
- LLVM 后端在 M6 接入，复用同一份 MIR；一期不写 LLVM IR。
- **不改造** `工具\cjc\Cjc.java` 的中文→Java 文本转译链路；新前端独立实现。
- 仓库结构固定为：

```
原生\
  驱动.ps1        对外入口（cjc.ps1 的「原生」子命令）
  驱动\           Java 命令行：检查 / 编译 / 运行 / 保留中间产物
  前端\           词法、语法、AST、语义、诊断
  中间表示\       HIR / MIR 定义、文本格式、解释器
  后端C\          MIR → C
  后端LLVM\       MIR → LLVM IR（二期）
  运行时\         C：启动、字符串、数组、集合、对象、异常、GC、IO
  测试\           对拍脚本、黄金快照、差异白名单
  工具\           词表桥接等构建期脚本
文档\原生\ADR\    架构决策记录
```

## 理由

1. 现有词表、诊断与 35 课回归都在 Java 侧，前端用 Java 可以直接复用数据与经验。
2. 产物不能依赖 JVM，因此代码生成与运行时必须是 C；C 后端生成的代码可人工阅读，便于定位语义问题。
3. 手写递归下降比引入语法解释器更可控，诊断文案能精确到中文词与列号。
4. 与现有链路解耦后，任何新前端的回归都不会影响 `.\cjc.ps1 检查 教程` 与 35 课行为。

## 替代方案

| 方案 | 不采用的原因 |
| --- | --- |
| Rust 全栈 | 前端需重写，学习与构建成本高；二期可评估 |
| C++ / Go | 生态与前端复用均不占优 |
| 直接复用 `Cjc.java` 的文本替换 | 没有 AST 与类型信息，无法生成正确代码 |
| 用 ANTLR 等生成器 | 中文词表与诊断定制受限，生成物难审阅 |

## 验收口径

- M0：`.\cjc.ps1 原生 检查 教程` 可调用，且不触碰 Java 转译链路。
- M1 起：新前端只读 `工具\cjc` 下的词表，`原生\` 内不得出现词表副本。
- 每个里程碑结束时，`.\cjc.ps1 检查 教程` 与 35 课输出保持不变。

## 影响

- 新增 Java 前端代码放在 `原生\`，不进入 `标准库\src`，不参与 Maven 打包。
- 新增 C 代码需兼容 MSYS2 MinGW-w64，构建脚本不得依赖 CMake。
- 驱动脚本保持 PowerShell 5.1 兼容：用 `;` 而非 `&&`，UTF-8 写回显式使用 BOM。
