# ADR-005 C 后端与行号

- 状态：已接受（M0）
- 日期：2026-11-09
- 关联：路线图第 6.2、6.4 节

## 结论

一期后端把 MIR **降级为 C 源文件**，由 clang 编译并链接：

- 生成文件放在 `构建\原生\<模块>.c`，仅作中间产物，不入库。
- 每个 MIR 指令前输出 `#line <中文源行号> "<中文源相对路径>"`，使 clang 诊断与调试信息指向中文源。
- C 标识符统一改写为 `_cjk_<码点十六进制>` 形式（如 `_cjk_5e8f_53f7`），并在上方用注释保留原名。
- 字符串字面量按 UTF-8 输出，运行时统一转为 UTF-16 码元。
- 编译参数：`-O2 -std=c11 -fwrapv -fno-strict-aliasing -static`；链接 `原生\运行时` 静态库。
- clang 路径探测顺序：`C:\msys64\mingw64\bin\clang.exe` → PATH 中的 `clang`；都找不到时输出中文安装指引并退出码 2。

## 理由

1. C 后端上手快，生成的 C 可人工阅读，语义问题容易定位到具体行。
2. `#line` 是 clang 原生能力，能把「中文源第 5 行」直接带进报错与 DWARF，避免自研行号表。
3. `-fwrapv` 让有符号整数按补码回绕，与 JVM 的 32/64 位回绕一致；`-fno-strict-aliasing` 规避激进别名优化带来的未定义行为。
4. 中文标识符直接写进 C 虽被 C11 允许，但跨编译器与工具链支持不一；转义成 ASCII 标识符最稳。
5. 绝对路径探测避免已打开终端不继承系统 PATH 的问题。

## 替代方案

| 方案 | 不采用的原因 |
| --- | --- |
| 直接生成 LLVM IR | 一期无 LLVM 绑定，开发与调试成本高；M6 再做 |
| 直接生成机器码 | 工作量不可控，且无法复用优化器 |
| 保留中文标识符原名 | 不同 clang/gcc 与调试器对 UTF-8 标识符支持不一致 |
| 只输出 `.s` 汇编 | 失去 C 的可读性与跨平台再编译能力 |

## 验收口径

- M3：01–08 课的 exe 与本机 JVM 后端 stdout、退出码逐字节一致。
- 故意制造类型错误时，clang 报错行号指向中文源对应行，而不是生成的 C 行号。
- 用 `objdump` 或崩溃栈能定位到中文源文件与行号。
- 缺少 clang 时，驱动给出中文安装指引且退出码为 2，不产生半成品 exe。

## 影响

- 生成 C 的命名、缩进与注释格式需稳定，便于 diff 与人工检查。
- 运行时接口一经确定（字符串、数组、对象、异常），C 后端与标准库实现必须共同遵守。
- 优化集中在 clang 的 `-O2`，一期不自研优化 pass。
