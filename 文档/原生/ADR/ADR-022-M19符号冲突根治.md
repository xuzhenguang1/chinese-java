# ADR-022：M19 符号冲突根治（包名进类名）

- 状态：Accepted（2026-11-23 用户拍板 G1–G3；同日复核实测后拍板改走方案 A 全量根治）
- 日期：2026-11-23
- 关联：后续路线计划书-M19至M22 第 3 节、M13/spec.md:68,110（明确标记「根本解决另立里程碑」）、ADR-017（多文件模块）、ADR-021（跨文件自举不动点）、ADR-007（符号口径）
- 前置：M0–M18 全部交付，双矩阵 CI 全绿（run 45173797419），35 课四路对拍 + 105 份快照 + 175 组不动点零回退，ADR 21 份，校验节 8.0–8.17

## 背景

M18 跨文件能力落地后，不同中文包下的同名类（如 `演示.甲.工具` 与 `演示.乙.工具`）在同一程序中仍是符号冲突隐患：C/LLVM 后端的 `编码()`（`C生成器.java:2349`、`LLVM生成器.java:3305`）只接收简单类名，逐码点 hex 编码不含包路径，两个同名类会产出同一符号，链接期重定义。M13 spec 明确把「包名进编码，根本解决」标记为「另立里程碑」，本 ADR 兑现该承诺。

**2026-11-23 开工实测推翻了计划书的一个核心假设**：计划书设想「只改 `编码()` 实参传全名、算法体不动、MIR 快照零回退」。但实测用模块命令编译示例工程（3 包 10 源），产出的 MIR 类名是 `类 主程序` / `类 学生` / `类 数值工具` 等**纯简单名，完全不含包信息**。根因：

1. 参考侧 `语义分析器.java:438`：`收集类` 对顶层类直接取 `声明.名()`，`编译单元.包名()` 从未进入类名；`转类型()`(:3178) 也用源码简单名构造 `类型.类类型(名)`。
2. 自举侧 `自举前端.java`：AST 的 `编译单元节点`(:1159) 连包名字段都没有，`解析包声明()`(:1831) 只做语法校验便丢弃包名；`收集类`(:3987) 顶层全名同样等于简单名。

**结论**：后端拿不到包名，就没有「全名实参」可传。要真正根治，必须让**类名（定义名 + 所有类型引用名）在 MIR 层就带包**，这触及两侧前端的类型系统，而非仅改后端 6 个函数。用户 2026-11-23 在充分知晓该成本后拍板「坚持 A 全量根治」。

G1/G2/G3 决策（2026-11-23 已拍板）：

- G1：符号编码用「全限定类名逐码点 hex」（算法体不动，只改类名本身）。
- G2：保留旧简单名符号别名过渡，M22 收官时统一清理。
- G3：保留「模块内简单类名唯一」诊断作为额外约束，端到端仍禁止同名类。

**G2+G3 组合张力**：G3 使端到端无法触发同名类，G1 的根治能力只能靠后端层单元测试证明。故采用**双轨验收**：策略层（G2/G3）端到端零回退，能力层（G1）用绕过诊断的后端层单测直接喂同名类 MIR 给生成器，断言符号分流。

## 决策

### 1. 命名规则（两侧对称）

顶层类的 MIR 名改为 `包名 + "$" + 简单名`（如 `演示.基础$数值工具`）；嵌套类继续 `外层全名 + "$" + 简单名`（如 `演示.基础$数值工具$嵌套`）。用 `$` 而非 `.` 与既有嵌套类分隔符保持一致；`编码()` 逐码点 hex 会把 `$`(0x24) 也编入，不同包天然不同符号。

**无包类保持简单名不变**：包名为空时顶层类名仍为 `声明.名()`。这是 35 课快照零回退的关键——35 课实测 0 个包声明（已核实），类名一律不变，MIR/AST/语义 105 份快照与自举不动点的 35 课 × 5 命令部分逐字节不受影响。

### 2. 参考侧改动点（`原生/中间表示/src/.../语义分析器.java`）

1. `收集`/`收集声明`(:384/:397)：把 `编译单元.包名()` 透传给 `收集类`。
2. `收集类`(:430/:438)：顶层类名拼包名前缀；嵌套类递归仍用 `外部.名 + "$" + 名`。
3. `查找类名`(:3301)：新增「简单名末段匹配」——先直接查类表（无包类/内建类/已全名），再查类表中以 `"$" + 名` 结尾的键（G3 保证简单名唯一，至多一个用户类命中），再走嵌套查找。
4. `转类型`(:3178)：`default` 分支对自定义类类型用 `查找类名(名)` 得到带包全名，再 `类型.类类型(...)`；内建/基本/文本/对象类型保持原名。
5. 方法体中所有经 `解析类`/`查找类名` 解析的类引用（新建对象、静态字段读、继承判断、捕获类型等）自动带包。

### 3. 自举侧对称改动点（`原生/自举/自举前端.java`）

必须与参考侧逐字节一致，否则打破 A/B/参考三方不动点：

1. `编译单元节点`(:1159)：新增包名字段 `包名`；`解析`(:1808) 接收 `解析包声明()` 的返回值并写入；`解析包声明`(:1831) 改为返回拼好的包名字符串（`"包."` 分段用 `.` 连接，空包返回空串）。
2. `收集类`(:3987)：顶层 `全名 = 包名.isEmpty() ? 声明.名 : 包名 + "$" + 声明.名`；嵌套仍 `外部.全名 + "$" + 声明.名`。
3. `查找类名`(:5479)：同参考侧末段匹配规则。
4. `转类型`（自举对应方法）：同参考侧 `查找类名` 映射。
5. `收集速览`(:8534)：`类|` 行的全名同样拼包（与参考侧 `前端主程序.java` 速览一致）。
6. `类头`(:6189)：已用 `符号.全名`，随全名变化自动带包，无需改逻辑。

### 4. 后端：编码调用点零改动 + G2 别名

- `C生成器.java` 20 处 / `LLVM生成器.java` 19 处 `编码(类名)` 调用点**不改**——类名本身带包后自动产出全名 hex（这是方案 A 相对计划书「改 39 处实参」的修正：改类名即可，调用点零风险）。
- `编码()` 算法体零改动。
- 内建类 / 标准库描述符判断（`内建类名.contains(类名)`、`标准库描述符类名.contains(类名)`）针对的是不带包的内建/标准库类，保持简单名后判断照常有效。
- G2 旧别名：C 侧为带包符号生成旧简单名 `#define` 别名；LLVM 侧用 `alias`。别名只覆盖顶层类的主要符号（结构体/描述符/构造器/新建函数），过渡期到 M22。别名范围与 M22 清理时机在本 ADR 冻结，后续不得随意扩大。

### 5. G3 策略不变 + 双轨验收

- 端到端：同名类仍被中文诊断「模块内简单类名唯一」拦下，行为零回退；旧别名可用。
- 能力层：新增后端层单元测试，绕过诊断层构造 `演示.甲.工具` 与 `演示.乙.工具` 两个同名类的 MIR 程序，喂给 C/LLVM 生成器，断言：①结构体/描述符/方法符号 hex 串不同；②生成的 C/LLVM 源码链接无重定义。这是 G1 根治能力的唯一实证。覆盖继承/构造器/静态字段/异常类型组合。

- 改造前 `自举前端.mir.txt` SHA256 `3324cb5a965f331bd3b2dc9b91180f9b1a0a0df6d5ac4ff6732ae86046e8bcb1` —— 冻结为 `自举前端.M18.mir.txt` 只读对照。
