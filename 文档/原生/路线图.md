# 中文原生编译路线图

> 目标（已定）：中文源码直接产出 **Windows x64 本机可执行文件（`.exe`，PE 格式）**，单文件、双击运行、运行时不再依赖 JVM。架构预留跨平台，但一期不承诺 ELF / Mach-O。
>
> 现状：`cjc` 已实现「中文 → Java 源 → JVM 字节码（`.class`）」；`.class` 是二进制，但仍需 JVM 解释/JIT 后才能变成机器码。
>
> 本文只谈架构、分期与验收，不含工期承诺。

---

## 1. 结论先行

1. **现在已经做到「中文 → 二进制（JVM 字节码）」**，缺的是最后一段：不经过 JVM，直接生成本机可执行文件。
2. **不存在「中文词直接查表变二进制」的捷径**。中文词只解决词法层；要生成机器码，必须有词法、语法、语义、中间表示、后端、运行时、链接七层。
3. 主线（已定）：**Java 写前端与驱动 + C 写运行时 + C 后端起步、LLVM 后端二期**，目标直指自研后端产出 PE，不走 GraalVM 演示路线。
4. 能力范围用现有 35 课教程做语法闸门：每个阶段以「第 N 课在原生后端的 stdout、退出码与 JVM 后端逐字节一致」为验收；标准库按第 14 节决策先行完整落地，语法范围仍按课逐步扩展。

---

## 2. 「二进制」的三种含义

| 层次 | 产物 | 现状 | 是否需要 JVM |
| --- | --- | --- | --- |
| JVM 字节码 | `.class` | 已有（`javac`） | 需要 |
| 本机可执行文件 | `.exe` / ELF / Mach-O | 无 | 不需要 |
| 机器码 / 汇编 | `.o` / `.s` | 无 | 不需要 |

本路线以**本机可执行文件**为最终验收物；`.class` 继续保留，作为参考后端与对拍基准。

---

## 3. 为什么不能「中文词 → 二进制」直接映射

- 中文关键字表只描述「哪个词等价于 `public` / `for` / `class`」，不包含类型、内存布局、调用约定。
- 真正的二进制需要回答：`整数` 是 32 位还是 64 位、对象字段怎么排、方法怎么调用、数组越界怎么处理、异常怎么展开、内存谁来回收。
- `清单.加入`、继承、接口、泛型、`流.过滤` 这些都不是词法替换能解决的，必须经过语义分析与中间表示。
- 因此正确路径是：

```
中文源 → 词法 → 语法树 → 语义（类型/符号） → 中间表示 → 后端 → 目标文件 → 链接运行时 → 可执行文件
```

## 4. 两条路线

### 路线 A：快速验证（复用现有链路）

```
中文源 → cjc 转译 → Java 源 → javac → .class → GraalVM native-image → exe
```

- 优点：几乎不改现有代码，最快拿到「双击就能运行」的演示。
- 缺点：不是自研编译器；exe 体积大、构建慢；反射与动态特性受限；报错仍来自 Java 工具链；无法按中文语义定制。
- 定位：**演示与需求验证**，不作为长期架构。

拟用命令（需先装 GraalVM）：

```powershell
mvn -f 标准库\pom.xml package
.\cjc.ps1 编译 教程 -d 构建\教程
native-image -cp "构建\教程;标准库\target\cjc-stdlib-1.0.jar" 第01课你好世界 构建\原生\第01课
```

### 路线 B：自研编译器（主线）

```
中文源 → 前端 → HIR → MIR → C / LLVM IR → 目标文件 → 链接 libcjkrt → 本机可执行文件
```

- 真正的「中文语言实现」，可控制语义、诊断、内存布局与性能。
- 前端用 Java（复用词表与现有诊断经验），运行时用 C，后端先 C 后 LLVM。
- 与现有 JVM 后端并存，互为参考实现，用对拍锁定行为。

**推荐：A 只做一次演示，B 作为主线。**

## 5. 目标架构

```
中文源（沿用 .java 扩展名，教程文件不改）
   │
   ├─ 词法：复用 关键字表 / 近义词典，产出 Token
   │        诊断沿用 CJK001 / CJK002 / CJK106
   ├─ 语法：手写递归下降，产出 AST
   ├─ 语义：名称解析、类型检查、装箱、导入解析
   │
   ▼
HIR（带类型、已脱糖：插值 / 重复 / 否则若 / 入口 / 切换表达式）
   │
   ▼
MIR（基本块 + 三地址 + 显式类型）
   ├─ MIR 解释器（先跑通语义，不依赖后端）
   ├─ C 后端   → 生成 C（带 #line） → clang -O2 → .o
   └─ LLVM 后端 → 生成 LLVM IR      → clang / llc → .o
                                        │
                                  链接 libcjkrt（C 运行时）
                                        ▼
                                  .exe / ELF / Mach-O
```

目录建议（与现有 `工具\cjc` 解耦，避免影响 35 课与全量校验）：

```
原生\
  驱动.ps1            对外入口，cjc.ps1 的「原生」子命令转发到这里
  驱动\               Java 命令行：检查 / 编译 / 运行 / 保留中间产物
  前端\               词法、语法、AST、语义、诊断
  中间表示\           HIR / MIR 定义、文本格式、解释器
  后端C\              MIR → C
  后端LLVM\           MIR → LLVM IR（二期）
  运行时\             C：启动、字符串、数组、集合、对象、异常、GC、IO
  测试\               对拍、黄金快照、模糊测试、基准
文档\原生\ADR\        架构决策记录
```

**词表只有一份**：前端直接读 `工具\cjc\关键字表.txt`、`近义词典.txt`、`方法糖.txt`、`诊断中文表.txt`，禁止复制到 `原生\` 下。语法用递归下降手写，不引入语法解释器。

## 6. 关键技术决策

### 6.1 实现语言

| 方案 | 前端复用 | 机器码生成 | 生态 | 结论 |
| --- | --- | --- | --- | --- |
| Java 25 + C 运行时 | 直接复用词表与经验 | 交给 clang / LLVM | 现有工具链成熟 | **推荐** |
| Rust 全栈 | 需重写前端 | inkwell 绑定 LLVM 最佳 | 学习成本高 | 二期可选 |
| Go | 需重写 | cgo 调 LLVM 较弱 | 简单 | 不推荐 |
| C++ | 需重写 | 原生 | 构建复杂 | 不推荐初期 |

Java 适合写词法、语法、语义、IR、驱动与测试；JDK 25 的 `record` / `sealed` / 模式匹配很适合描述 AST。运行时必须是 C（或 Rust），因为产物不能依赖 JVM。**不要用 Java 手写 x86 指令编码。**

### 6.2 后端

| 方案 | 上手速度 | 优化能力 | 调试 | 结论 |
| --- | --- | --- | --- | --- |
| C 后端 + clang | 快 | 强（`-O2`） | 生成 C 可人工检查 | **一期** |
| LLVM IR | 中 | 最强 | DWARF 行号 | **二期** |
| QBE | 快 | 弱 | 一般 | 教学备选 |
| 直接机器码 | 极慢 | 无 | 差 | 不采用 |

### 6.3 中间表示

- HIR：带类型的 AST，已完成脱糖。
- MIR：控制流图 + 基本块 + 三地址码；类型只保留 `i8/u16/i32/i64/f64/ptr/struct`。
- 先做 **MIR 文本格式 + 解释器**，语义问题在解释器阶段暴露，不要等代码生成后再查。
- MIR 文本同时作为黄金测试的快照。

### 6.4 值表示与对象模型

- 基本类型不装箱：`整数`→`i32`、`长整数`→`i64`、`双浮点`→`f64`、`布尔`→`u8`、`字符`→`u16`。
- 引用类型：指向对象头 `{ vtable*, class_id, gc_header }`，字段紧随其后。
- 数组：`{ length, element_kind }` + 连续数据；读写前插入越界检查。
- 泛型：一期擦除 + 装箱（与 Java 语义一致，便于对拍）；二期按需单态化优化。
- 空引用用 0 指针，解引用前插入空检查。
- C 标识符不能直接用中文：统一改写为 `_cjk_5e8f_53f7` 形式，`#line` 与原名注释保留可读性。

### 6.5 字符串

- 一期内部用 **UTF-16 码元**，与 Java `String` 的 `length` / `取字符` / `取子串` 完全一致，降低对拍成本。
- 输入输出边界做 UTF-8 转换；Windows 控制台需设置 UTF-8 代码页。
- 插值在 HIR 阶段降为字符串拼接，运行时不感知 `{}`。

### 6.6 异常

- 一期：`setjmp` / `longjmp` + 每线程异常处理器栈；`尝试` / `捕获` / `兜底` 直接映射。
- 运行时维护函数符号表（函数名、源文件、行号），异常时打印中文栈。
- `声明抛出` 只做编译期标注，原生后端不强制检查。
- 二期：改用 LLVM 的 DWARF 展开，或返回码 + 检查。

### 6.7 内存回收

| 方案 | 依赖 | 风险 | 结论 |
| --- | --- | --- | --- |
| Boehm 保守 GC | 第三方库 | 低 | **一期推荐** |
| 自研标记-清除 | 无 | 中 | 二期 |
| 引用计数 | 无 | 循环引用泄漏 | 不推荐 |
| arena / 不回收 | 无 | 长循环内存增长 | 仅 M3 临时方案 |

### 6.8 语义兼容清单（写入 ADR，并用对拍锁定）

| 语义点 | Java / JVM | C 默认行为 | 处理 |
| --- | --- | --- | --- |
| 整数溢出 | 按 32/64 位回绕 | 有符号溢出是未定义行为 | 用无符号运算或 `-fwrapv` |
| 整数除法 | 向零截断；除零抛异常 | 除零未定义 | 插入除零检查 |
| `整数.最小 / -1` | 回绕为最小整数 | 未定义 | 特判 |
| 移位 | 移位数自动取模 | 超宽度未定义 | 先掩码 |
| 数组越界 | 抛 `数组越界异常` | 未定义 | 每次读写插检查 |
| 空引用 | 抛 `空指针异常` | 段错误 | 每次解引用插检查 |
| 字符串拼接 `空` | 输出 `null` | 未定义 | 运行时统一处理 |
| 浮点打印 | 最短可回读表示 | `%g` 结果不同 | 移植 Ryu 或 Java 的浮点转文本算法 |
| 集合遍历顺序 | `HashMap` 顺序不保证 | 自研哈希表顺序不同 | 对拍只用 `链式键值表`，或在白名单里登记 |
| 默认 `哈希码` | 身份哈希 | 地址哈希 | 不比较具体数值 |

其中**浮点打印**与**无序集合遍历**是「逐字节一致」的两大难点，必须在 ADR 里定性，不能等测试失败再补。

## 8. 测试与质量

1. **对拍（核心）**：同一中文源分别跑 JVM 后端与原生后端，比较 stdout 字节、退出码；stderr 只比较关键行。
2. **差异白名单**：`原生\测试\差异白名单.txt` 登记允许不同的项（无序集合遍历、浮点暂用近似格式等），每条必须对应 ADR，禁止口头豁免。
3. **黄金快照**：AST 与 MIR 文本快照，改动必须显式更新。
4. **诊断一致性**：把 `校验.ps1` 的诊断反例同时跑两套前端。
5. **模糊测试**：随机 Token 序列保证不崩溃、不挂起。
6. **内存检查**：Linux 用 ASan / valgrind；GC 压力用例。
7. **性能基准**：递归 fib、长循环、字符串拼接、键值表读写，分别对比 JVM 与原生。
8. **跨平台 CI**：Windows（clang 或 MSVC）与 Linux（clang）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 双后端语义漂移 | 同一程序两种结果 | 对拍 + 差异白名单 + ADR |
| 浮点打印不一致 | 输出无法逐字节比对 | 一期移植 Ryu，或明确白名单 |
| 无序集合顺序不同 | 对拍误报 | 测试统一用 `链式键值表` |
| 异常 + GC 复杂 | 崩溃、内存泄漏 | 一期用 setjmp + Boehm，限定范围 |
| 泛型 / 接口 / 流 | 范围爆炸 | 擦除起步，流只做最小子集 |
| C 未定义行为 | 偶发错误结果 | 溢出、除零、越界、移位全部显式检查 |
| 工具链缺失 | 无法产出 exe | 驱动自动探测 clang，缺失时给出安装指引 |
| 词表漂移 | 两套实现不一致 | 单一数据源 + 校验脚本 |
| 过早优化 | 进度失控 | 先正确后优化，优化集中到 M6 |

## 12. 与现有仓库的衔接

- **不改造 `Cjc.java` 的文本转译链路**：它面向「中文 → Java 源」，缺少 AST 与类型；新前端独立实现，避免破坏现有 35 课与全量校验。
- **复用词表与诊断经验**：关键字、近义词、方法糖、诊断中文表保持单一数据源。
- **保留 JVM 后端**：作为参考实现与对拍基准，不删除。
- **标准库双实现**：Java 版继续服务 JVM；C 运行时按同名中文 API 重写，用对拍锁定行为。
- **文档位置**：本路线图与 ADR 放 `文档\原生\`，不占用根目录。

## 14. 决策与待定项

1. **目标产物**：**已定** —— Windows x64 本机 exe（PE），单文件、双击运行、不依赖 JDK；目标三元组 `x86_64-w64-windows-gnu`，用 `C:\msys64\mingw64\bin\clang.exe` 链接。架构预留跨平台，但一期里程碑不承诺 Linux ELF / macOS Mach-O。`.class` 保留为参考后端与对拍基准。
2. **实现语言**：**已定** —— Java 前端 + C 后端。前端复用现有词表与诊断；MIR 先降为 C（带 `#line` 保留中文源行号），由 clang 链接成 PE；LLVM 后端按 M6 二期接入。不采用 Rust 全栈，不先做 GraalVM 演示。
3. **首批范围**：**已定 —— 先完整标准库**。`输出` / `文本` / `数值` / `时间` / `文件` / `集合工具` / `并发` / `网络` / `日志` / `数据` 共 10 类，在 C 运行时里按现有 Java 实现的公开 API 逐项落实，再扩展教程覆盖。
   - 执行顺序：标准库依赖对象模型与字符串/集合，实际顺序为 M2 语义 → M3 基础 C 后端 → M4 对象模型 → 标准库运行时（M5 前半提前）→ 教程 22–35 对拍。
   - 验收口径：以 `标准库\src` 的公开方法清单为准逐项勾销；未实现的 API 必须给出明确中文诊断，不允许静默返回或返回空值。

拍板后按 M0 → M1 开工，每个里程碑都以可运行产物和真实命令输出收尾。
