## 1. 总览：为什么按 M19 → M20 → M21 → M22 排

四个方向存在清晰的「地基 → 能力 → 外延 → 收官」依赖，不按选择顺序平铺：

```
M19 符号根治 ──(包名进编码，后端符号地基)──┐
                                             ├→ M22 自举七期收官（生产路径替换，最敏感，最后动）
M20 运行时二期 ─(异常/泛型/浮点，运行时地基)┤
                                             │
M21 平台与生态 ─(Mach-O/registry/LSP，外延)─┘
```

| 顺序 | 里程碑 | 排序依据 |
| --- | --- | --- |
| M19 | 符号冲突根治（包名进编码） | 改 `编码()` 是全后端共享的符号地基，越早做，后续里程碑的符号验证越干净；M13 spec 明确标记「根本解决另立里程碑」的技术债；**已实证不动 `编码()` 规则即可保 35 课快照与不动点**（自举前端无编码逻辑，MIR 用中文名） |
| M20 | 运行时二期（DWARF 异常展开 · 泛型单态化 · 浮点根治） | 三块都改运行时/后端语义，必须在符号地基稳定后做；其中浮点根治直接消除 M16 登记的唯一已知差异，收益明确 |
| M21 | 平台与生态（Mach-O · registry/semver · 完整 LSP） | 外延扩展，依赖前两块的地基稳定；三者相互独立，可内部并行 |
| M22 | 自举七期收官（生产路径替换） | 改动面最大、最敏感——把自举 exe 提升为生产编译器，必须在符号、运行时、平台全部冻结后进行，否则替换后任一地基变动都要重做不动点 |

## 3. M19 符号冲突根治（包名进编码）

### 3.1 目标 / 非目标

**目标**：让不同中文包下的同名类在 C/LLVM 后端产出**不同的 C 符号 / LLVM 符号**，根治跨包同名类合并时的重定义冲突，把 M13 的「模块内简单类名唯一」临时约束升级为真正的全限定名唯一。

**非目标**：

- 不改 MIR 文本格式与中文标识符（`MIR快照/` 35 份零回退）。
- 不改自举前端（实证：自举前端无 `编码()` 调用、无 `_cjk_` 生成，不动点不受影响）。
- 不改 JVM 后端与 `Cjc.java` 转译链路。
- 不改运行时 ABI（`cjk_value` / `jmp_buf` 布局等）。
- **不改诊断层行为**：按 G3 保留「模块内简单类名唯一」诊断作为额外约束，同名类在端到端仍被禁止（策略不变）；M19 只把符号地基能力修到位，不解锁该约束。

### 3.2 现状切入点（已核实）

| 位置 | 现状 | 切入点 |
| --- | --- | --- |
| `后端C/C生成器.java:2349-2360` `编码()` | 逐码点 hex + `_` 连接，只接收简单类名 | **必改**：编码输入改为全限定类名 |
| `后端LLVM/LLVM生成器.java:3305-3315` `编码()` | 同上，两份独立实现 | **必改**：与 C 后端同一算法 |
| `C生成器.java` 20 处 / `LLVM生成器.java` 19 处 `编码()` 调用 | 传入的多为 `类.名()`（简单名） | **逐个核对**：类定义、vtable、构造、静态初始化、枚举、方法、字段、异常类型处传全名 |
| `M13/spec.md:68,110`、`tasks.md:39` | 明确「MVP 简单类名唯一，根本解决包名进编码另立里程碑」 | 本里程碑兑现该承诺 |
| `M18/对拍自举模块.ps1` | 专用样例 6 文件，跨包导入 | 新增「两包同名类」正负例 |
| `示例工程/` 3 包 10 源 | 当前无跨包同名类 | 新增一对同名类验证根治效果 |

### 3.3 核心设计

**编码方案**（G1 已拍板，2026-11-23 实测修订）：全限定类名逐码点 hex + `_` 连接，与简单名编码 `工具` 的 hex 串不同，从而天然区分同名类。要点：

- **实测修订（重要）**：原设想「只改 `编码()` 实参传全名」不成立——2026-11-23 编译示例工程实测 MIR 类名是纯简单名（`类 主程序` / `类 学生`），`编译单元.包名()` 从未进入类名（参考侧 `语义分析器.java:438`、自举侧 `自举前端.java:3987` 均丢弃包名）。**后端拿不到包名，无可传的全名实参**。
- **方案 A（用户 2026-11-23 拍板全量根治）**：让类名本身在 MIR 层带包——顶层名改为 `包名$类名`（如 `演示.基础$数值工具`），嵌套类 `外层$内层`。这要求**两侧前端对称改造**：参考侧 `语义分析器.java` 的收集类/查找类名/转类型，自举侧 `自举前端.java` 的 AST 包名字段/解析包声明/收集类/查找类名/转类型/速览。
- **后端零改动**：`C生成器.java` 20 处 / `LLVM生成器.java` 19 处 `编码()` 调用点**不改**——类名带包后自动产出全名 hex；`编码()` 算法体不动。这是方案 A 相对原计划「改 39 处实参」的修正，把风险从后端收敛到前端类型系统。
- 无包类保持简单名（35 课 0 包声明，快照天然零回退）。内建/标准库类不带包，后端 `内建类名.contains` 判断照常有效。
- 详见 ADR-022。

**兼容性**（G2 拍板：保留旧简单名符号别名过渡）：新符号用全限定名 hex，同时为旧简单名符号保留别名（C 侧 `#define` / 弱别名，LLVM 侧 `alias`），过渡期保证外部引用与既有产物不因符号改名断裂。别名范围与移除时机写进 ADR-022：建议 M20 前为过渡期，M22 收官时随生产路径替换一并清理（届时同名类约束或已解除）。

**G2+G3 组合张力及处置（重要）**：G3 保留「简单类名唯一」诊断 ⇒ 端到端仍禁止同名类 ⇒ G1 全限定名编码的「区分同名类」能力**没有端到端用例能触发**。为不让 M19 退化成「改了编码却无法验证根治效果」，采用**双轨验收**：

- **策略层（遵守 G2/G3）**：端到端行为零回退，同名类仍被中文诊断拦下；旧简单名别名可用。
- **能力层（验证 G1 地基）**：新增**后端层单元测试**——绕过诊断层，直接构造「两包同名类」的 MIR 程序喂给 C/LLVM 生成器，断言两者产出的符号 hex 串不同、链接无重定义。这是 M19 根治能力的唯一实证，也是未来（G3 若解除）解锁同名类的地基验证。

**验证面**：MIR 快照 35 份、自举不动点 175 组**理论上零回退**（自举前端不产 C 符号）；实际需实跑确认，若发现快照变化即为 bug 而非预期。

## 4. M20 运行时二期（DWARF 异常展开 · 泛型单态化 · 浮点根治）

### 4.1 目标 / 非目标

**目标**：兑现路线图第 6 节二期项——异常从 `setjmp/longjmp` 升级为 DWARF 栈展开（LLVM）、泛型从擦除装箱升级为按需单态化、浮点打印消除 M16 登记的唯一已知差异（`Double.MIN_VALUE` 次正规数）。

**非目标**：

- 不改 MIR 文本格式（单态化在后端特化，不改 MIR 降级输出）——若实测必须改 MIR，按 **G4 预授权**冻结旧副本 + A/B 双实现交叉确认重生成基线（沿用 M18 F3-A），不中途另立决策。
- **G5 拍板「双后端都改」**：C/LLVM 双后端均从 setjmp/longjmp 升级到 DWARF 栈展开，**不保留双轨**。C 后端 `jmp_buf` 探针值 200 / handler 216 布局可随展开改造调整（不再是冻结项）；`cjk_frame` 帧链两后端均保留供中文栈回溯。
- 不引入 Rust 后端、不做 LTO/-march（M12 已测无收益）。

> **G5 口径变更（2026-11-24 拍板推翻原计划）**：原 §4.1/§4.3/§4.5 的「仅 LLVM 启用 DWARF、C 保留 setjmp 双轨」作废。理由：双轨意味着异常语义两套实现长期并存，C/LLVM 对拍一致性需持续兜底；统一到 DWARF 后仅一套异常控制流，`cjk_frame` 只负责中文帧名打印，长期维护与故障面更小。代价：C 后端异常 ABI 变动需重跑 M16 已验证的异常/对拍用例，风险高于双轨——故列为 M20 三块中最后一块，前两块（浮点根治、泛型单态化）零回退后再动。

### 4.3 核心设计

**三块内部按风险递增排序**：浮点根治（局部、收益明确）→ 泛型单态化（后端特化）→ DWARF 异常展开（最大）。

- **浮点根治**：现状算法「从 p=0 递增找可回读最短位数」对次正规数过早停止。修复方向：对 `p` 找到的最短十进制，验证其是否唯一区分相邻 double；若不唯一则提高位数至唯一（对齐 Java FloatingDecimal 的 `dtoa` 规则）。改后撤销 `浮点已知差异.txt` 的 MIN_VALUE 登记，ADR-007 删该已知限制条。`%f`（`%.6f`）独立口径不变。
- **泛型单态化**：在 C/LLVM 后端对 `cjk_object*` 值盒按实参类型生成特化版本（如 `cjk_list_int32` / `cjk_list_object`），保留 `__值` 的 MIR 文本表示不变；对拍验证特化后输出与擦除版逐字节一致。若某泛型形态特化成本过高，保留擦除回退并在 ADR 说明。
- **DWARF 异常展开（G5 双后端都改）**：C/LLVM 两后端均生成展开 landing 逻辑（LLVM 用 `landingpad` + Itanium ABI personality；C 侧对应生成 personality 调用与 landing 分支），共同替代 `longjmp`；`cjk_frame` 帧链两后端均保留供中文栈回溯（DWARF 只负责控制流，中文帧名仍由运行时打印）。C 后端异常 ABI（探针 200 / handler 216）不再是冻结项，随展开改造调整。对拍要求异常用例（第 20/21 课）C/LLVM/JVM 三方逐字节一致。

| G4 | 单态化若必须改 MIR 文本 | A. 不改 MIR、实测必须改则停下对齐 ／ B. 预授权冻结基线重生成 | **B. 预授权基线重生成** | §4.1 非目标与硬门槛改写：按 M18 F3-A 冻结旧副本 + A/B 交叉确认，不中途对齐；T4.1 增基线迁移动作 |
| G5 | DWARF 异常展开范围 | A. 仅 LLVM、C 保留 setjmp（双轨） ／ B. C/LLVM 双后端都改 | **B. 双后端都改** | 推翻 §4.1/4.2/4.3/4.5 原双轨口径；C 后端新增展开改造切入点、异常 ABI 不再是冻结项；T3.1/T3.2 改写；§4.6 增两条新风险；ADR-023 定义统一异常口径 |
| G6 | 浮点根治是否做 | A. 根治（推翻 M16 不修结论） ／ B. 维持登记不修 | **A. 根治** | §4.3 浮点根治维持 T1.1/T1.2；撤销 ADR-007 已知限制第 2 条与 `浮点已知差异.txt` 的 minvalue 行；对拍浮点 7/7 须无「已登记差异」 |

> **G5 是三块中风险最高的一块**：C 后端异常 ABI 变动会波及 M16 已验证的异常/栈回溯用例，故 §4.3 的推进顺序锁定为「浮点根治 → 泛型单态化 → DWARF 展开」，前两块零回退后才动第三块。单轨化后不再有 setjmp 回退路径，若 C 侧展开无法与 JVM 对齐，须回到用户重新对齐（不自动降级为双轨）。
